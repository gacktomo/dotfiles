# /saas-analysis — SaaS / デジタルサービス分析

SaaS やデジタルサービスの Web サイト URL を受け取り、ビジネス観点で構造化された
分析レポートを生成する。分析フレームワークは hmhm (wicle.io) のサービス分析の
観点を参考にしている。

引数: `$ARGUMENTS` — 分析対象のサービス URL（例: `https://asoview.co.jp/service`）。
URL が渡されていなければユーザに尋ねる。

---

## 進め方

1. **対象サイトを読む** — `WebFetch` で対象 URL を取得し、サービス概要・主要機能・
   ターゲット・料金・トーンを把握する。トップページだけで情報が薄ければ、
   `/pricing` `/about` `/features` などの下層ページも追加で取得する。
2. **市場・競合を調べる** — `WebSearch` で「サービス名 + 競合」「業界 + SaaS 比較」
   などを検索し、競合サービスと市場文脈を補強する。推測で埋めず、出典を確認する。
3. **7 セクションで構造化** — 下記フレームワークに沿ってレポートを作成する。
4. **出力** — 既定では会話に Markdown で提示する。ユーザがファイル保存や
   Artifact 化を望めばそれに従う。

> 情報が取れなかった項目は「不明／要追加調査」と明記し、断定的な創作はしない。
> 一次情報（対象サイト）と推測・一般論は区別して書く。

---

## 分析フレームワーク（7 セクション）

### 1. 基本情報
- **サービス概要**: 1〜2 行で要約
- **ビジネスモデル**: SaaS / マーケットプレイス / 広告 / 従量課金 など。収益源を特定
- **プロダクトフェーズ**: 立ち上げ / 成長 / 成熟 のいずれか（根拠も）
- **業界分類**: 業界・カテゴリ

### 2. ペルソナ分析
対象となる代表的なユーザータイプを **3 種類** 想定（例: マーケター / 事業責任者 /
デジタルマーケティング責任者）。各ペルソナについて:
- **ニーズ**: 達成したい具体的な成果目標（1 文）
- **悩み**: その達成を阻む現状課題を **3〜4 項目** の箇条書き。各悩みに背景状況を一言添える

> ニーズと悩みを対応させる。例:「予約率の最大化」（ニーズ）⇔「施策効果の証明困難」
> 「離脱理由の不透明さ」（悩み）。

### 3. 価値と課題
**価値**:
- コア価値を 1〜2 行で要約
- 主要機能を **表形式**（機能名 / 詳細説明）で列挙

**課題（導入障壁）**: 3 フェーズに分類し、各課題に改善優先度（高 / 中 / 低）を付与:
- **獲得フェーズ**（導入時）: 認知・検討・契約までの障壁
- **定着フェーズ**（活用時）: オンボーディング・継続利用の障壁
- **スケールフェーズ**（拡大時）: 組織展開・上位プラン移行の障壁

### 4. AARRR 成長モデル
5 段階それぞれについて:
- **課題の背景**: 1 段落
- **推奨アクション**: 3〜4 項目（施策名 + 実行内容）
- **検討用の問い**: 4〜5 個（深掘りのためのAI質問例）

段階:
1. **Acquisition（獲得）** — どう知ってもらうか
2. **Activation（活性化）** — 初回の「アハ体験」をどう作るか
3. **Retention（定着）** — どう継続利用させるか
4. **Revenue（収益）** — どう収益化・単価向上するか
5. **Referral（紹介）** — どう紹介・拡散を促すか

### 5. グロースモデル
- サービスの **自己強化ループ（フライホイール）** を文章 + 簡易図で可視化する。
- マーケットプレイス型なら「供給増 → 選択肢増 → 需要増 → 供給増」のような
  両面ネットワーク効果を示す。SaaS 型なら「利用 → データ蓄積 → 価値向上 → 継続」など。
- 図は Mermaid（`graph LR`）または ASCII で表現してよい。

### 6. 競合分析
- **直接競合 3 社**: 各社の強み・弱みを段落で詳述し、自社（対象サービス）の優位性を簡潔に整理
- **その他競合**: 表形式（サービス名 / 特徴 / ポジション）でコンパクトに列挙
- **ポジショニング**: 軸（価格 × 機能、汎用 × 特化 など）で対象サービスの立ち位置を示す

### 7. AI代替耐性
LLM・AI エージェントの普及によって、サービスのどの価値が代替・コモディティ化
しうるかを評価し、堀の持続性を判定する。

- **代替リスクの棚卸し**: §3 の主要機能・価値ごとに、AI に代替されやすいか／
  されにくいかを **高 / 中 / 低** で評価。代替されやすい例＝一般知識の要約、
  テキスト生成、公開情報の集約、定型的なワークフロー。
- **堀の源泉**: 以下のうち該当するものを挙げ、持続的優位の有無を確認する:
  - 独自データ / プロプライエタリなデータ蓄積（AI も取得できないもの）
  - ネットワーク効果 / 両面市場
  - 物理的制約・リアルワールド実行（現地・ハード・オペレーション・物理計算）
  - 規制・ライセンス・法的参入障壁
  - スイッチングコスト / 既存ワークフローへの埋め込み・統合
  - ブランド・信頼・コミュニティ・UGC
- **AI を梃子にできる余地**: 脅威としてだけでなく、AI で強化・効率化できる機能
  （守りと攻めの両面）。
- **判定**: 総合的な AI 代替耐性を **高 / 中 / 低** で示し、根拠と
  「耐性を高めるために投資すべき領域」を 1〜2 点。

検討用の問い（深掘り用）を 4〜5 個添える。例:
- このサービスのコア価値は、汎用 LLM ＋公開データで再現できてしまうか？
- 競合が AI ネイティブで参入した場合、最初に侵食される機能はどれか？
- 蓄積データは「AI が学習・取得できないもの」か、それとも公開情報の再整理か？
- AI を組み込むと、堀が深まるか／逆にコモディティ化を早めるか？
